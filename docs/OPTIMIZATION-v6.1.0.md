## 二、修复域一：订阅拉取 Connection reset 根治（SUB-RESET · Net.java / SubscriptionManager.java）

### 2.1 根因

订阅市场 3 源全部走 `cdn.jsdelivr.net`——国内运营商对 jsdelivr 类海外 CDN 间歇性 TCP 重置（Connection reset）；而旧镜像变体链 `mirrorVariants()` 只对 npmmirror / gkd-kit / raw.githubusercontent 三类 URL 生成变体，**对 jsdelivr 本身零回退**——三源同 CDN 同命运，一旦被运营商重置便没有任何备用通道，导入必失败。

| 现象 | 根因 |
|---|---|
| 订阅市场点击导入 →「拉取失败 Connection reset」 | 3 源全部 cdn.jsdelivr.net + 国内运营商间歇性 TCP 重置 |
| 失败后重试也没用 | 旧变体链对 jsdelivr 零回退——同一 URL 原样重发，重置依旧 |

### 2.2 修复：mirrorVariants() 新增规则④——jsdelivr gh URL 五变体全链

| 通道 | 性质 |
|---|---|
| ① cdn.jsdelivr.net（原始 URL） | jsdelivr 原始接入点 |
| ② fastly.jsdelivr.net | 同 CDN 另一接入点 |
| ③ ghfast.top | 代理 GitHub raw |
| ④ gh-proxy.com | 代理 |
| ⑤ raw.githubusercontent.com | GitHub raw 直连 |

### 2.3 Net.httpGetRaw()——同址瞬时故障重试 + 超时调优

| 项 | v6.0.0 | v6.1.0 |
|---|---|---|
| 同址重试 | 无 | 瞬时故障重试 1 次（间隔 600ms——只对 reset/timeout/EOF 等**瞬时性故障**重试；HTTP 4xx/5xx 立即换址：服务器明确拒绝，重试无意义） |
| 连接超时 | 10s | **7s** |
| 读取超时 | 15s | **12s** |
| UA | — | 浏览器风格（CDN/代理站友好）；GitHub API 路径仍用原 UA |

快速失败快速切镜像——死等 10s 不如 7s 换通道。**最坏 10 次出手（5 变体 × 2 次重试）任一成功即导入成功。**

### 2.4 humanizeNetError()——错误人话化（5 类）

底层异常翻译成人话，例如 Connection reset →「网络连接被运营商/CDN 重置（jsdelivr 类海外源在国内间歇性被干扰，稍后重试或换网络通常可恢复）」——用户看到的不再是天书报错，而是「发生了什么 + 该怎么办」。

## 三、修复域二：误触二轮三防线（MISFIRE-FGH · core/HumanTap.java F/G/H + AdSkipService.java 接线）

用户实锤：「设备类型/分辨率原因导致多点误点——1比1模拟人在不同设备上操作使用卫士解决该bug」。v6.0.0 已做 A~E（人手参数散布 / 复验节奏放缓 / 耐心预算 6 / dp 归一 / 轨迹去重）；本轮 1:1 模拟继续，针对残余多点误点的**三条真实路径**补三道纯函数防线：

### 3.1 三条残余多点路径 → 三道防线机制表

| 防线 | 常量 | 机制 | 根治的多点路径 |
|---|---|---|---|
| **F 同指纹目标去抖**（sameTargetKey / isFiredRecently） | SAME_TARGET_QUIET_MS=1500ms | 点击已派发后 1.5s 内同指纹目标（**包名 + 中心坐标容差网格化 + 语义标签哈希**）绝不再出手 | 点击已生效但广告跳转有 300~800ms 动画延迟——复验扫描看到「按钮还在」再点一次 = 用户肉眼的多点 |
| **G 出手前新鲜度复核**（isStaleBounds） | STALE_DRIFT_RATIO=0.5 + STALE_DRIFT_MIN_DP=24dp | 出手时 re-fetch 节点最新 bounds（getBoundsInScreen）——中心位移超过 max(旧矩形短边×50%, 24dp×density) 判为动画位移中 → 放弃本次出手、等下一轮扫描用新 bounds；节点已不可见/消失 → 绝不盲刺 | 「点它现在在哪」而不是「它曾在哪」——位移中盲点旧坐标=误点 |
| **H 结果静默期**（postTapQuietOk） | POST_TAP_QUIET_MS=250ms | 手势成功派发后同包 250ms 内任何新候选不再出手 | 真人完成一次点击后物理上不可能 0ms 连续再点——机器连发正是反自动化 SDK 触点检测的直接特征 |

### 3.2 服务侧接线（AdSkipService.java）

- `execute` 的 A_CLICK_BOUNDS / A_CLOSE / A_TAP_POINT 三个分支出手前查 F/H，成功后记录 firedTargetAt / lastGestureOkAt
- `clickNode` 出手前做 G 复核
- 新窗切换 `clearTapGuards` 同步清零——防线只在同窗内生效，跨窗绝不误伤
- `firedTargetAt` 256 条防膨胀兜底

## 四、修复域三：日志增强（LOG-3XDAILY · AdSkipService.java）

### 4.1 参数对比表

| 参数 | v6.0.0 | v6.1.0 |
|---|---|---|
| AUTO_LOG_MS（自动提交间隔） | 12h | **8h——一天自动提交 3 次、24 小时均匀（8h/16h/24h 三个时点；成功才计时、息屏/服务未运行跳过等下轮心跳，绝不夜间耗电）** |
| MAX_LOG 留存 | 120 条 | **300 条** |
| buildLogBody 上报携带引擎日志 | 16 条 | **40 条（带时间戳）** |
| 重点事件留存段 | 无 | **从 300 条留存窗反查四类重点事件统计（误触防护/自愈拉活/订阅异常/引擎预警）+ 最近 6 条重点事件原文** |
| 标题/文案 | 12 小时口径 | 「（8 小时自动 · 一日 3 次）」 |

### 4.2 为什么是 8h：一天 3 次 24 小时均匀

8h/16h/24h 三个时点把 24 小时均匀铺满；成功才计时（失败当轮不重置计时窗，下轮心跳再试）；息屏/服务未运行跳过等下轮心跳——**绝不夜间耗电**（不为准点提交把设备从深睡里拉起来）。

### 4.3 留存 300 条 + 重点事件留存段

120→300 条覆盖完整开屏周期——订阅拉取失败/自愈/误触防护等重点低频事件不再被高频命中日志挤出。上报时从 300 条留存窗反查四类重点事件统计（误触防护/自愈拉活/订阅异常/引擎预警）+ 最近 6 条重点事件原文——用户问的「什么类型要重点留存」，答案直接写在上报里。

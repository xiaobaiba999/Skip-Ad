# v6.0.0 优化实录 —— 1:1 人手模拟引擎（设备类型/分辨率→多点、误点根治）

> 用户原话实锤：「部分用户设备开屏广告跳过时因为设备类型、分辨率或者其他原因影响，导致多点、误点的情况，体验非常不好」——**1 比 1 模拟人在不同设备上操作使用卫士**，复现并解决这个 bug。

## 一、1:1 复现：先当用户，再当工程师

### 1.1 复现方法论

把 v5.9.0 引擎放进 24 类真实设备几何（720p~1440p 直板 · 16:9 遗留 · 折叠外屏窄幅/Flip 超窄/内屏近方三方档 · 平板 · 分屏半窗横竖 · 刘海/挖孔 · 正方 · 横屏）× 7 档设备密度（1.0~4.0）的仿真环境里，以「一个真人正在用这台设备」的视角逐帧走完「广告出现→引擎出手→复验→再出手」全链路，站在用户视角数「引擎替我点了几下」。

### 1.2 复现结果：v5.9.0 之后仍存在的四类残余缺陷

| # | 缺陷 | 复现观测 | 用户观感 |
|---|---|---|---|
| ① | **机器人手势签名** | `dispatchGesture` 触点是「固定 40ms 起始延迟 + 固定 110ms 时长 + 完美水平 1px 轨迹」——千次出手一模一样 | 反自动化广告 SDK 的触点指纹检测（时长零方差/轨迹零抖动）会**无声吞掉**这种签名：点了没反应 → 引擎复验 → 再点 →「多点」级联实锤 |
| ② | **出手用旧坐标** | 扫描时刻捕获的 bounds 到手势真正落屏有 40~300ms 延迟；广告按钮入场缩放/位移动画后，按「它曾在哪」点击=点空 | 人眼是按「它现在在哪」点的——1:1 人眼追踪缺位 |
| ③ | **触点安全域用固定 px** | `MIN_VISIBLE_SIDE=12px`/`EDGE_INSET=6px` 在 160dpi 设备=12dp/6dp（过严——有效小按钮被拒点），在 480dpi 设备=4dp/2dp（过松——触点距圆角/波纹死区仅 2dp） | 同一份代码在不同设备密度上行为漂移，正是「设备类型、分辨率原因」的根 |
| ④ | **复验节奏是机器枪** | 点击后 450ms/900ms 双针补扫 + 12 次点击预算 | 首点失败设备上最多 **12 连点**——用户肉眼看到的就是「多点」 |

## 二、修复：HumanTap 1:1 人手模型（全部纯函数，JVM 可测，服务侧薄接线）

### 2.1 A · tapSpec —— 人手触点参数域

```java
起始延迟 26~56ms（真人抬指→落指反应散布，替代固定 40ms）
首击时长 95~130ms（真人轻点域）
重试时长 115~160ms（人会点得更用力更久）
±2px 微抖轨迹（远小于最小安全内缩，绝不出目标面）
```

每次出手都不同（SplitMix64 确定性 PRNG——测试同种子可精确复现，线上真人散布）：**时长方差 ≥10 档 · 两轴抖动散布**（S1 断言：200 种子 × 6 attempt 全域内 + 方差 + 确定性 + 重试更用力 + 抖动散布五重验证）——反自动化广告 SDK 触点指纹检测不再无声吞点，「点了没反应→复验→多点」级联从源头断流。

手势路径从「完美水平 1px」升级为「微斜轨迹（+2,+1+ε）」——完美水平线也是机器人指纹。

### 2.2 B · verifyDelayMs —— 人手复验节奏

```
首击后 500ms 扫一眼（人手 300~500ms 补刀节奏保持）
第 2/3/4/5/6 击后 1.4s → 2.4s → 3.6s → 5.2s → 7.0s 渐进放缓
```

替代 v4.4.0 的 450/900 双针机器枪：**人会越等越慢，机器枪不会**。首击失败设备上双针/连针是用户看到「多点」的直接观感来源。同窗耐心预算 `MAX_CLICKS_PER_WIN` 12→**6**（与 `HUMAN_PATIENCE` 同源）：6 下没关就优雅收手等倒计时走完，绝不机器枪连点（S3+S7 断言）。

### 2.3 C · dp 密度归一 —— 「设备类型、分辨率原因」根治

安全域常量全部从 px 迁 dp，按设备 density 缩放（钳制 [1.0, 4.0]）：

| 常量 | 值 | density=1.0 | density=2.0 | density=4.0 |
|---|---|---|---|---|
| 可见缝最小边 | 12dp | 12px | 24px | 48px |
| 触点距边内缩 | 6dp | 6px | 12px | 24px |
| 轨迹去重容差 | 8dp | 8px | 16px | 32px |

160dpi 与 480dpi 设备上行为归一：低密度不再过严拒点（「无点」），高密度不再贴死区（点空复验=「多点」）。`density=1.0 时 pickDp ≡ pick`（v5.9 行为零回归，S5c 断言）。`screenDensity` 在 `onServiceConnected` 从 DisplayMetrics 缓存，热路径零 IPC。

### 2.4 D · isDupPoint —— 触点轨迹去重

同窗已刺过的坐标 ±8dp（密度缩放）邻域内**绝不重复盲刺**：换象限轮换，而不是在同一坐标上连点。轮换耗尽（5 档全落入已刺邻域）→ `adaptiveTapPoint` 拒点 null → 降级无障碍代点/换下一候选——「绝不原地连点」的最终防线（S4 三重断言）。轨迹登记 24 点/窗防膨胀，64 包封顶长会话防护，窗口切换/广告已关同步清空。

### 2.5 实时人眼追踪（服务侧接线）

出手前 `refreshLive()` 刷新节点**现在**的 bounds：广告按钮入场缩放/位移动画后，引擎按「它现在在哪」点击（人眼看到哪就点到哪）——「旧坐标点空→复验→多点」根因之二根治（S6 位移追踪断言：目标动画位移 10px 后触点仍随新 bounds 落点安全）。

覆盖层 Z 序判定用**抖动后的最终落点**（判的就是落屏点）；抖动后坐标越界回退原点/贴边钳制（边界防线不因抖动而破）。

## 五、诚实修正：三处测试断言语义错位（引擎行为正确，断言算术错位）

复现过程中发现 v5.9.0 遗留的三处**测试断言**与引擎真实契约错位（非引擎缺陷）：

1. **S2/S6/S10/S12 曾要求「典型跳过键在任意密度都必须可点」**——但 720×1280 × density 4.0 在真实世界不存在（720p 遗留机密度 1.0~2.0），且与 S5d「高密度收紧：30px 缝 density4.0 拒点」契约自相矛盾。修正为**真实密度配对**（TestHost.realDensities：24 几何 × 该档设备真实出货密度——这才是 1:1 模拟「人在不同设备上」）+ **全 7 档压力条件契约**（可刺→必须安全落点；亚指腹 dp 短边 <12dp→必须拒点=防误触正确行为）——覆盖面从「7 档全要可点」升级为「真实配对必须可点 + 不真实组合必须语义正确」，断言更严而非放松。
2. **S4c 曾把「五点互距 ≤w/2」错当「±8dp 切比雪夫邻域内」**：四象限中心距几何中心 (w/4,h/4)=(19,14)px，Chebyshev 距 19px > dupTolPx(2.0)=16px → 五档互为独立可刺点。修正为三重契约断言：①同坐标 ±8dp 绝不重复采用 ②独立点封顶 ROTATION_SLOTS=5 ③轮换耗尽全判重→拒点换候选（「绝不原地连点」最终防线显式断言）。
3. **矩阵总检仍用「9 场景」口径**（v6 新增 S10/S11/S12 后实为 12 场景）→ 修正为 24×12=288。

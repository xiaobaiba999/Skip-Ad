# v7.2.0 优化实录（2026-11-19）——信息流广告真机命中根治（李跳跳方法论）+ 白名单全量应用列表 + 报告饼图折叠 + 多点防线 I

> 本轮主题：**用户十二轮实锤的四处真机病灶全部根治**。v7.1.0 的信息流广告卫士 81 项单测全绿但真机零命中——本轮以李跳跳实测方法论为参照，逐层挖出四处「单测测不出、真机必踩」的死因并根治；白名单/报告/版本记录三处 UI 实锤同步落地。全程测试对准病灶（不做无意义测试），17 套件 4077 项 JVM 断言全绿（+10）。

## 一、信息流广告「全都没拦截」四处死因与根治（本轮主战场）

**用户实锤原话**：扫描日志上传未命中问题，app内穿插的广告全都没拦截，关于这一块的实现可以参考李跳跳的实现逻辑（李跳跳在同类场景可关闭 app 内广告）。

### 死因① armed 在菜单弹出的瞬间被清零（最直接死因）

v7.1.0 的 `AdSkipService.clearTapGuards()` 在**每次窗切换**时执行 `feedArmedPkg = null`。而 P1 点角标拉起的关闭菜单**本身就是 Dialog/Popup 新窗**——`TYPE_WINDOW_STATE_CHANGED` 一到，armed 立即被清零。P2 的 8s 指纹窗在菜单出现的 100ms 内死亡，后续永远等不到收菜单的机会。

**修复**：armed 绝不在窗切换时清零——它只由 ①P1_ARM_MS（8s）自然过期 ②P2 完成 ③切换到其他应用（`pkg.equals(feedArmedPkg)` 门）复位。P2 直通窗闸：armed 期间不看窗类/窗计时（菜单是 Dialog 新窗是常态而非异常），安全性由中性项精确等值 + 扩展动作排除 + 形态闸承担。

### 死因② 窗闸双杀（sns 窗门 + 12s 开屏窗闸）

菜单 Dialog 作为新窗把 `winClass` 覆盖成菜单窗类 → `isFeedWindow`（微信只认 sns 族窗）失败；同时 `windowAt` 重置 → 12s 开屏窗闸阻断 → 双杀。

**修复**：armed 直通上述两闸；非 armed 路径窗闸 `WINDOW_MS(12s)` → `FEED_START_MS(2.5s)`——朋友圈等信息流窗不是开屏窗，旧 12s 保守闸把头几屏 feed 扫描全部饿死；开屏链与 feed 同窗时由点击冷却自然互斥。

### 死因③ 预算制 DFS 够不到深层卡片（李跳跳方法论替换）

300 节点预算的手写 DFS 在朋友圈大树上只爬到前几张卡片——深处理广告的角标**永远扫不到**。这是单测全绿（测试树只有几个节点）而真机全灭（真树几百上千节点）的典型错位。

**修复（李跳跳方法论主路径）**：`AccessibilityNodeInfo.findAccessibilityNodeInfosByText(词)` 原生直查——C++ 侧全树 contains 搜索，预算无关，深埋卡片的角标/菜单项同样查到。命中节点包装为候选交给 `FeedAdGuard.decideP1FromCandidates / decideP2FromCandidates`（本轮新增纯函数）逐候选过完整语义（精确等值）+ 形态（≤35%屏×≤8%屏）闸——宁漏勿误红线与 DFS 路径完全一致，只是「爬树」换成「直查」。DFS 保留为兜底。`BADGE_WORDS`/`neutralCloseWords()` 开放给服务侧逐词直查。

### 死因④ P2 双闸在真机菜单上零命中

真机微信角标菜单常只露出 1 个中性项（如仅「不感兴趣」）→ 旧「强特征≥1 且总数≥2」双闸全灭 → 菜单永远不收。

**修复**：armed（P1 刚出手）本身即最强上下文信号——**armed 且中性项 ≥1 即出手**（李跳跳式）；非 armed 依旧零动作（用户自己长拉的菜单绝不对抗）。同时收编真机文案两族：「屏蔽此推广」（强特征·旧版朋友圈）、「减少此类广告」（弱·菜单变体）。

### 附带根治：armed 期回落 P1 的角标连点

v7.1.0 的 `fd==null → decideP1` 兜底在 armed 期（菜单尚未拉起）会**再点一次角标**——角标被连点即用户可见的「多点」。本轮 armed 期间**只走 P2**，绝不回落 P1。

### 配套

- P2 节流 350ms 快节奏复查（`P2_SCAN_THROTTLE_MS`）；
- **信息流关闭单独记账**：P2 完成时 `bumpStat(pkg, "feed")`；feed 路径不再计入 auto 战绩（P1 拉菜单是中间动作）——报告饼图「信息流关闭」一档真实可见；
- **feed 未命中诊断日志**：feed 名单窗内常规扫描零角标 → 30s 节流记「🔍 信息流未命中」行，随一日三次日志上传——用户反馈「全没拦截」时，日志能区分「窗内无角标（基线）」与「角标文案未收编（要扩词表）」。

## 二、白名单全量应用列表（用户二选一提问——双方案一起落地）

**用户实锤**：应用白名单搜索不到，不符合人的使用行为，搜索应该像浏览器那样，我输入qqQQ无论大写小写都能检索到，或者直接把所有应用显示出来。

**根因**：`MainActivity.whitelistJson()` 列表来源 = 白名单 ∪ 引擎战绩 byApp（上限 80 条）——新装用户/没拦截记录的 App（QQ、微信……）根本不在列表里，搜索必然找不到。

**修复（两个方案都给）**：
1. **全量应用列表**：`queryIntentActivities(ACTION_MAIN + CATEGORY_LAUNCHER)` 枚举全部已安装可启动应用（label 用 `getApplicationLabel`），∪ 白名单 ∪ 引擎战绩三源合并，`Collator(CHINA)` 中文序、白名单置顶，上限 80→500；30s 内存缓存（增删白名单即时失效，防勾选态回弹）；
2. **浏览器式搜索**：中文名/包名双通道**不区分大小写**包含匹配（`qqQQ` → `qq` → 命中 `QQ`），120ms debounce 实时过滤，列表滚动区 460px 细滚动条，placeholder 明示「不区分大小写」。

## 三、卫士使用报告：饼图常驻 + 明细折叠 + 到页自动刷新

**用户实锤**：卫士报告生成之后增加折叠功能，不然太长看着挺难受的，或者直接不显示也行，整个饼图在那，用户到此页面再刷新。

**修复**：报告重写为「饼图 + 折叠」形态——
- **饼图常驻**：纯 CSS `conic-gradient` 甜甜圈（112px），五段：开屏秒跳 / **信息流关闭（新）** / 弹窗关闭 / 返回键 / 反馈面板收起；中心总数；旁边图例（色块+名称+次数）；全 0 时灰色整环 +「暂无拦截记录」；绿色系五档配色（沿用应用色板，零蓝色）。
- **五段折叠明细**（默认全收起，点标题行展开/收起）：拦截战绩 / 订阅两源命中 / 应用战绩 Top5 / 能耗画像 / 设备画像——行格式与数据来源（全本机零上传）原样保留。
- **到页自动刷新**：进入「我的」tab 静默重渲染（零 toast）；按钮改「刷新报告」。

## 四、多点误点防线 I（设备触点被吞的连击从源头掐断）

**用户实锤（保持自 v6.0 起的原话）**：部分用户设备开屏广告跳过时因为设备类型、分辨率或者其他原因影响，导致多点、误点。

v6.0/v6.1 已做 A~E + F/G/H（人手参数散布/复验节奏放缓/耐心预算/dp 归一/轨迹去重/同指纹静默/新鲜坐标/结果静默）。本轮补第四道纯函数防线并收紧节奏：

- **防线 I 同指纹击数封顶**：`MAX_STRIKES_PER_TARGET=2` + `targetStrikesOk`（纯函数·JVM 可测）——同一目标指纹（包名+容差网格坐标+语义标签）每窗最多 2 击，第 3 击起静默；换候选/换窗不受限。服务侧 `firedTargetCount` 表随窗切换清零。
- **耐心预算 6→3**：`MAX_CLICKS_PER_WIN` 与 `HUMAN_PATIENCE` 同源收紧——人的耐心就是 2~3 下。
- **F 同指纹静默 1500→1600ms**（同目标再击至少间隔 1.6s——人手双击下限）。
- **H 结果静默 250→600ms**：复验扫描 500ms 到点时静默未过则不补击，下一轮 1.4s 再评——「点了还没生效就再点」的多点观感从节奏上根治。
